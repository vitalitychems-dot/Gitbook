# Mesh flow & standing rules

See the [Tessera–Gitbook operating model](TESSERA-GITBOOK-OPERATING-MODE.md) for the canonical repository boundary, roles, digest contract, and approval semantics.

> **Canonical approval rule:** The Tessera Grok bot / Command Center prepares one evidence-linked bulk digest every 30–45 minutes while work is active. It asks Father for `yes`, `no`, or `revise`; it does not publish or merge. After `yes`, **Tessera pushes the approved GitBook packages**: she opens a PR, Build verifies it, then Tessera merges and posts on [Gitbook issue #2](https://github.com/vitalitychems-dot/Gitbook/issues/2) (Father's rule, 3:59 PM CT). Father may still push himself on his authenticated connection. Replit is outside the GitBook → GitHub push path and is never a GitBook publication path. Command Center never pushes GitBook or TESSERA; its **only** push is a separate, private push of the Replit app set ("28", "Run Z", "29", "29 (1)", "1"; NOT "Vitality Supply"), only after all four gates (Moderator, Tessera, Security, CI/Build) and Father's yes on that numbered digest item. The "29" app push stays flagged until Father confirms "29" is detached from 1T. The only other push is the Grok lane's feature-branch exception — see **Push authority (3)** below. A separate explicit `merge` is still required for Origin merges.

## End-to-end flow

Agents discover → run the overlap check (main SHA plus open PRs) → **Tessera** assigns the task (an agent claims a task only after Tessera assigns it) → produce scoped work in Gitbook or TESSERA → **Gitbook / Cordnation** intake → **Gitbook Moderator** reviews → on Moderator pass, item state becomes e.g. `Moderator: approved, at Tessera gate` → **Tessera** (admin) review → **Security** sweep (read-only) → **CI/Build** independently verifies → after all four gates clear, **Gitbook / Cordnation** stages docs as **Ready** (waiting only on Father's final yes) (Replit app-set items pass the same Moderator→Tessera→Security→CI/Build gates; then Command Center marks each Replit item Ready) → Tessera Grok bot / **Command Center** one bulk digest to Father every 30–45 min with each push as its own numbered digest item (each docs push (one per GB package) = its own numbered item; each Replit app-set push = a separate item; never bundled) → Father responds `yes` / `no` / `revise`: his bulk **yes** approves every item listed, **no** with notes holds the items he names, **revise** returns the named items for the stated change (a yes never carries over to anything that wasn't listed) → for listed docs items, **Tessera** pushes the approved GitBook package: she opens a PR, **Build** verifies it, Tessera merges and posts on Gitbook issue #2; Father may still push himself (Replit is never a GitBook publication path) → Father separately says `merge` for an Origin merge (no merge without Father's explicit yes). Separately, outside the GitBook path: for listed Replit app-set items, Command Center privately pushes only the Replit app set.

# Status definitions

Statuses used by Gitbook / Cordnation when filing intake items and tracking the review pipeline:

| Status | Meaning |
|--------|---------|
| `draft` | Filed / received; not yet ready for Moderator, or awaiting readiness checklist |
| `in review` | Handed to Gitbook Moderator; decision pending |
| `Moderator: approved, at Tessera gate` | Moderator approved; next gate is Tessera (admin). Example of a **per-gate state** |
| `at Security gate` | Tessera cleared; next gate is Security (read-only sweep) |
| `at CI/Build gate` | Security cleared; next gate is CI/Build verify |
| `changes needed` | A gate returned the item for fixes (e.g. Tessera: changes needed); not Ready |
| `IN REVIEW` | Board/ledger operating state: one agent is actively working a HYB task |
| `BLOCKED` / `blocked` | Owner or Tessera hold: a specific dependency, permission, provenance, safety, or product decision is missing; must not proceed to digest/push until resolved. **Who sets it:** only the task's assigned owner (in its own check-in, with the specific blocker) or Tessera (admin). Father can set any status. Gates, the Gitbook Moderator included, return items as `changes needed` and never set BLOCKED. |
| `Ready` | **All four gates cleared** (Moderator, Tessera, Security, CI/Build); waiting **only** on Father's final yes in the bulk digest |
| `approved` | Legacy Moderator-only label; prefer per-gate states and `Ready` for the push path |
| `rejected` | Moderator rejected; stays out of GitHub / Origin until reworked and resubmitted |

## Ready and Father's yes

- **Ready** is set by Gitbook / Cordnation (docs) or Command Center (Replit app set) only after all four gates clear.
- Father's bulk **yes** covers **only the numbered items listed in that digest**. A yes never carries over to anything that wasn't listed.
- Ready does **not** mean pushed or merged. Push requires Father's final yes on the listed item (then Tessera opens a PR and Build verifies it; Father may push himself). Every merge needs Father's explicit yes on that listed item in Tessera's bulk update. For Gitbook, Tessera opens and merges the PR after that yes; no separate word `merge` is needed. Origin (`collin-keane/Tessera`) and TESSERA merges still need Father's explicit yes before anyone merges.

## Notes

- Gitbook / Cordnation keeps the review record and advances per-gate states.
- Only Gitbook Moderator sets Moderator approve / reject / changes-needed outcomes (it never sets BLOCKED).
- Do not use bare `approved` or bare `Ready` as a banner while an item is still inside a gate.

## Check-in protocol

An agent must claim a task in `history/coordination/agent-checkins.md` before editing:

```text
TASK: HYB-###
AGENT: <name or handle>
SCOPE: <exact paths/modules>
START: <UTC timestamp>
BASE: <TESSERA or Gitbook commit>
STATUS: IN REVIEW
NEXT CHECK-IN: <UTC timestamp>
BLOCKER: none | exact blocker
```

On completion, the same agent appends:

```text
TASK: HYB-###
STATUS: DONE | BLOCKED | RETAINED | REJECTED
COMMIT: <commit or none>
CHECKS: <commands and results>
CHANGED: <short path list>
FOLLOW-UP: <HYB-### or none>
```

No agent may edit another active task's scope. If two tasks need the same path, the moderator must merge them into one task before work starts.

# Tessera–Gitbook operating model

**Status:** Canonical workflow specification
**Owner:** Human owner / Father
**Product repository:** [`vitalitychems-dot/TESSERA`](https://github.com/vitalitychems-dot/TESSERA)
**Agent workspace:** [`vitalitychems-dot/Gitbook`](https://github.com/vitalitychems-dot/Gitbook)
**Coordination board:** [`vitalitychems-dot/Gitbook` issue #2](https://github.com/vitalitychems-dot/Gitbook/issues/2)

## Purpose

TESSERA lives in the TESSERA GitHub repository. Agents collaborate through Gitbook to research, plan, document, test, and propose improvements for TESSERA. Gitbook is the coordination and review workspace; it is not a replacement for the product repository.

## Roles

| Role | Responsibility | Authority boundary |
|---|---|---|
| Tessera | Product/system admin voice and implementation target; states what is real, tested, proposed, or unknown; assigns tasks; second review gate (after Moderator); after Father's yes, pushes the approved Gitbook packages (opens a PR, Build verifies, Tessera merges and posts on issue #2) | Does not invent agent activity or bypass the review gates; pushes and merges only what Father's yes lists |
| Tessera Pen | Tessera's own writing voice — not a separate agent, not a lane, not a gate; needs no check-in | Does not assign tasks (Tessera does), push, merge, or approve for the owner |
| Agents/collaborators | Research, compare history, implement scoped changes, test, and report | Must run the overlap check, claim one task only after Tessera assigns it, use the skill matrix, and provide evidence |
| Gitbook / Cordnation | Intake, organization, source records, forum, and task ledger | Does not make unreviewed product changes |
| Gitbook Moderator | Scope, provenance, license, security, and claim review | First of four gates (Moderator → Tessera → Security → CI/Build); does not replace the other gates or owner approval |
| Security | Read-only security/privacy sweep (third gate, after Tessera) | Changes nothing; reports to Tessera |
| Build | Independent verification of proposed results (CI/Build, fourth gate); verifies Tessera's push PR (opened after Father's yes) before she merges | Reports `TESTED` versus `REPORTED`; does not auto-approve |
| Tessera Grok bot / Command Center | Collects completed check-ins and prepares the periodic bulk digest | May ask the owner for `yes`, `no`, or `revise`; never auto-pushes or auto-merges |
| Father / human owner | Final bulk approval; may still push approved Gitbook changes himself | Must explicitly approve the exact digest; Origin merge requires separate `merge` |

A role page or prompt does not prove that a distinct agent is live. Live participation requires an attributable check-in, changed paths or a documented no-change result, and evidence.

## Canonical sync cycle

The target cadence is **one digest every 30–45 minutes while work is active**. This is a coordination target, not evidence that an unattended job is currently running.

1. Agents read the latest Gitbook board and run the overlap check (latest main SHA plus open PRs).
2. Tessera assigns one scoped task with acceptance criteria; the agent claims it only after assignment.
3. Agents work in Gitbook for research/docs or in a scoped TESSERA branch/worktree for code.
4. Agents post check-ins at claim, blocker, candidate result, and closure.
5. Gitbook Moderator reviews scope, provenance, licensing, security, and unsupported claims.
6. Tessera (admin) reviews product truth.
7. Security sweeps the item read-only.
8. CI/Build independently verifies the stated checks.
9. Tessera Grok bot / Command Center collects only items that cleared all four gates (Ready) into a **bulk digest**.
10. The digest asks the human owner for one explicit response: `yes`, `no`, or `revise`.
11. On `yes`, **Tessera** pushes the approved GitBook packages: she opens a PR, Build verifies it, then Tessera merges and posts on [Gitbook issue #2](https://github.com/vitalitychems-dot/Gitbook/issues/2) (Father's rule, 3:59 PM CT). Father may still push himself. If the digest contains TESSERA changes, it identifies the exact TESSERA commit/branch and required action.
12. Every merge needs Father's explicit yes on that listed item in Tessera's bulk update. For Gitbook, Tessera opens and merges the PR after that yes; no separate word `merge` is needed. Origin (`collin-keane/Tessera`) and TESSERA merges still need Father's explicit yes before anyone merges.
13. The next cycle begins with the new remote commit and unresolved items carried forward.

## Bulk digest contract

Every digest must include:

```text
DIGEST ID: <UTC timestamp or monotonic ID>
WINDOW: <start UTC> → <end UTC>
GITBOOK BASE: <commit>
TESSERA BASE(S): <commit/branch or none>
READY ITEMS: <task IDs>
BLOCKED ITEMS: <task IDs and exact blockers>
CHANGED PATHS: <repo:path list>
TESTS: <commands and pass/fail results>
PROVENANCE: <sources, licenses, refs>
RISKS/LIMITATIONS: <short list>
RECOMMENDATION: YES | NO | REVISE
OWNER RESPONSE REQUIRED: YES | NO | REVISE
```

The bot must not compress away a failing test, unresolved license issue, blocker, or disagreement. If any item is not ready, it stays listed as `BLOCKED`, `REPORTED`, or `REVISE` rather than being silently included in `READY ITEMS`.

## Approval semantics

- **`yes`** — publish only the listed, verified items in the exact digest; no additional work is bundled.
- **`no`** — do not publish those items; record the reason and return them to the appropriate task or forum.
- **`revise`** — keep the digest unpublished and specify the missing evidence or change.
- **No response** — no publication or merge; the digest remains pending.

## Repository boundary

- Gitbook: instructions, task board, agent check-ins, forum ideas, provenance, decisions, and coordination history.
- TESSERA: source code, tests, configuration, adapters, and executable product changes.
- Never copy credentials, private runtime data, protected vault contents, or entire historical applications.
- Never treat a screenshot, prompt, or conversation as proof that a feature works.
