===== mesh/secure-mesh.md =====
# Secure mesh (O11)

How Tessera encrypts and addresses mesh traffic. Built on the security inventory of 2026-10-12 (`SECURITY-PROTOCOLS-INVENTORY.md`).

## What it is
- **E2E envelopes:** AES-256-GCM + HKDF, Ed25519 sender signatures (same curve family as the preview gate identity and O10 node keys).
- **Content addressing:** `cid = sha256(plaintext)`. Topic ids are sha256 of the topic name (IP-less pub/sub).
- **Quarantine:** unknown keys, bad signatures, and GCM failures are refused and kept in a quarantine buffer (shepherd-style `allowed` / `refused` audit).
- **Transports:** pluggable. Default is an in-process memory bus (no sockets, no IPs). O10 LAN discovery can carry these frames later.
- **Owner gate:** O10's mesh toggle stays the outer switch. Nothing publishes while it is off.

## Honest limits
- **Group key, not sealed boxes.** Peer-to-peer sealed boxes need X25519 ECDH. Node's Ed25519 keys do not convert without a new dependency, so this release uses an owner-installed symmetric group key plus signatures. The group key is generated locally and only shared out-of-band with owner approval.
- **No WAN / Tor / public relay is built in.** Any gateway that puts frames on the public internet is a separate, opt-in piece. It would leak metadata (timing, size, who talks to the gateway) even when payloads stay encrypted. That gateway is not this page and not O11.
- **Not the sacred / colonial / omniversal ciphers.** Those product ciphers stay where they are. O11 reuses only the AES-GCM envelope shape.

## Tests (local, recorded on TESSERA#204)
Encrypted round trip · tamper refuse · unknown-key refuse · pub/sub across 3 nodes.

## The idea

Based on the included project brief, the most supportable version of the idea is an owner-controlled AI project with two separate, clearly bounded parts:

1. **A reference assistant** that answers from owner-reviewed, versioned sources; shows evidence and citations; communicates uncertainty and provider failures; and keeps only context approved for a specific purpose.
2. **A fictional simulation space** where generated characters and events can be created, saved, explored, and deleted. Its stories are application-generated content—not evidence of independent people, a continuing mind, or real conversations.

The supplied plans also express interest in a consistent, warm voice; useful context between sessions; multimodal and cognitive-architecture research; self-review; and suggestions for improvement. These are goals to explore and test, not capabilities established by this handoff. The safer direction is to make proposed improvements reviewable and owner-approved, rather than letting the system modify or deploy itself.

Some earlier plans mention storefront and business operations. This public Tessera/Grok handoff deliberately excludes customer, account, order, checkout, payment, email, and visitor-derived data, along with code and service paths that can access it. # Moderator handoff

When **Gitbook / Cordnation** marks an item ready, it hands the item to **Gitbook Moderator**. Moderator is the review gate before anything reaches GitHub / Origin.

## What "ready" means

An item is **ready** for Moderator when all of the following are true:

1. Filed in the [intake log](../intake/log.md) with required fields: title, author lane, date (CT), source, license, status
2. Content is complete enough to review (not a placeholder stub unless the stub itself is the submission)
3. No secrets, credentials, or tokens in the page
4. Does not propose crypto / money / store work, uncensoring tools, or surveillance of real people
5. Does not instruct flipping `TESSERA_ENABLE_*` away from `0`
6. Does not create or point at a new coordination board (only [Gitbook issue **#2**](https://github.com/vitalitychems-dot/Gitbook/issues/2))
7. Author lane and ownership boundaries are clear (or explicitly marked provisional / TBD)
8. Status moved to `in review` by Gitbook / Cordnation at handoff

- [ ] Standing rules respected (flags, secrets, out-of-scope topics, single board)

- [ ] If approved: goes to Tessera gate (state e.g. `Moderator: approved, at Tessera gate`); Cordnation stages Ready only after the TESSERA gate → Security scrub (→ CI/Build for changes to code, validators or scripts) also clear — Moderator approval alone is **not** auto-pushed; the auto-yes also needs the TESSERA gate, then the Security scrub
