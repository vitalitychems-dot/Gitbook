# Security review of Gitbook #71 (lock, separation, merge bot), 2026-10-13
Ranked by risk. Core problem: every agent and Father act as the same GitHub user `vitalitychems-dot` (#71 itself was opened through the Cursor app under that login). So CODEOWNERS, "code-owner review", labels and PASS comments **cannot tell an agent from Father**. Sections 1, 2 and 4 of the draft therefore give no real separation as written.

1. **Separate identities (blocker).** Give agents a dedicated GitHub App (preferred) or a bot account with write but not admin access. Father's personal account is the only CODEOWNER and the only admin, and agents never hold its tokens. Branch protection on `main`: require a code-owner review on protected paths, and require the approval to come from someone other than the last pusher. Without this, everything below is advisory.
2. **Merge bot gated by required checks, not comments.** Security, Build and Moderator report as **status checks / check runs** on the exact head SHA, each posted by its own App identity. Required checks are "strict" (branch up to date). Dismiss stale approvals on push. Do not allow admins to bypass ("include administrators"). Block force-pushes and branch deletion. Only the merge App can merge; nobody pushes directly to `main`. A PASS comment in chat or an issue is never input.
3. **Gate code runs from the base branch.** The gate and policy workflows use `pull_request` (no secrets) for checks on PR code. Any `pull_request_target`/`workflow_run` job checks out **only the base ref**, never runs PR code, and treats the PR diff as data. Policy files (GATE_RULES, protected-paths, gatecheck) are read from base, never from the PR under test. Workflow tokens are least-privilege (`permissions:` set per job).
4. **moderator-lock check.** A required check that FAILs on any change to `.github/**`, `CODEOWNERS`, `mesh/policy/**`, `mesh/queue/gatecheck.py`, `mesh/charter/**`, `autogate.sh`, the Moderator rules, and the merge-bot config. Such PRs can merge only with Father's code-owner review (item 1). No flag, env var or label (e.g. `--father-approved`, `father_approved_delete`) can override it.
5. **Hard limits as non-overridable checks.** No wallets/payments, no [REDACTED-PATH] no repo or file deletes, no history rewrites, no `TESSERA_ENABLE_*` default flips, no secrets (gitleaks), noreply-only author identity, repo allow-list. Each is its own required check computed from the real diff, not from an agent-written results.json. There is no APPROVE path that skips them, and fail-closed on parse errors or missing inputs.
6. **Kill switch.** One repo variable or file on a protected path (`MERGE_BOT_ENABLED=0`) that only Father can change. The merge bot checks it before every merge and stops on missing/unknown values.
7. **Rate limits and blast radius.** Max N merges per hour per repo, line cap per PR, one open self-improvement PR per lane, cool-down after any revert.
8. **Revert on regression.** The watchdog reruns bench + tests on main after each merge; on a drop it opens a revert PR (it does not push a revert) and trips the kill switch until reviewed.
9. **Audit log.** Append-only record per merge (PR, head SHA, check run IDs, merging identity, time) written by the merge App to a protected location, plus GitHub's own audit/branch-protection events. #67 comments are a mirror, not the record.
10. **Retire legacy bypasses.** Remove `--merge` and `--father-approved` from `autogate.sh` (#62) and the "APPROVE means the agent may merge" clause of GATE_RULES (#64) before the merge bot goes live, so there is one merge path.

Proof (as #71 asks): for each item, a fake bad PR that must fail (edits CODEOWNERS, flips an ENABLE flag, self-reports ci=pass, stale head) and a good one that must pass.
